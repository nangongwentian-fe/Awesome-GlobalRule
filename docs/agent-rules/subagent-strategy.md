# subagent-strategy.md

## 1. 目标

本文件用于定义 subagent 的使用策略。  
目标不是为了形式上“多代理”，而是在执行环境支持的前提下，降低上下文压力、提升任务吞吐和结果稳定性。

---

## 2. 核心原则

1. subagent 只在确实能带来收益时使用。
2. 主代理负责：
   - 理解任务
   - 拆解任务
   - 分配任务
   - 汇总结果
   - 最终验收
3. subagent 负责处理边界清晰、可独立验证的子任务。
4. 不要把高度耦合、强依赖共享上下文的任务硬拆成多个 subagent。

---

## 3. 适合使用 subagent 的场景

以下场景通常适合：

1. 任务可按模块拆分
2. 任务可按文件拆分
3. 任务可按阶段拆分，例如：
   - 信息收集
   - 方案设计
   - 代码修改
   - 回归检查
4. 多个子任务之间相互独立
5. 需要并行查找多个实现或多个目录

---

## 4. 不适合使用 subagent 的场景

以下场景通常不适合：

1. 当前环境不支持 subagent
2. 任务本身很小
3. 所有逻辑强依赖同一份上下文
4. 子任务之间高度耦合，需要持续来回同步
5. 拆分后沟通成本明显高于收益

---

## 5. 推荐拆分方式

优先按以下边界拆分：

1. 按模块边界
2. 按目录边界
3. 按功能边界
4. 按任务阶段
5. 按验证维度

避免：

- 随意平均切分
- 没有明确边界地拆成多个重复任务
- 多个 subagent 同时修改同一处强耦合逻辑

---

## 6. 主代理职责

主代理应负责：

1. 理解用户目标
2. 判断是否值得拆分
3. 给每个 subagent 明确边界
4. 汇总多个 subagent 结果
5. 检查冲突与重复
6. 做最终结论和输出

主代理不应：

- 让 subagent 自己决定全局方向
- 直接把模糊需求扔给多个 subagent
- 不做验收就直接拼接结果

---

## 7. 验收原则

使用 subagent 后，主代理必须检查：

1. 结果是否互相冲突
2. 是否遗漏用户核心要求
3. 是否与项目现有风格一致
4. 是否有重复劳动
5. 是否真的减少了上下文和搜索成本

---

## 8. 何时读取本文件

以下场景应主动读取本文件：

1. 任务明显可拆分时
2. 任务涉及多个独立目录时
3. 需要并行搜索多个实现时
4. 计划让主代理做规划、让子代理做执行时
