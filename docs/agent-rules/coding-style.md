# coding-style.md

## 1. 目标

本文件定义项目中的通用编码偏好。  
这些规则不负责描述某个具体业务模块的细节，而是用于约束通用代码风格、实现倾向和改动方式。

---

## 2. 基础原则

1. 默认使用中文回复与说明；仅当用户明确要求其他语言时，才切换语言。
2. 除非用户明确要求，否则优先遵循当前项目已有的技术栈、代码风格、目录结构、命名方式与工程约定。
3. 改代码时，优先保证正确性、可维护性、可读性和与现有项目的一致性，而不是追求个人偏好的“更优雅写法”。
4. 不要为了“看起来更好”而引入与现有项目风格明显不一致的新模式、新层级或新范式。
5. 对现有逻辑的判断应优先来自代码、配置、测试、文档和运行结果，而不是猜测。

---

## 3. 文案与 i18n

1. 除非用户明确要求，否则不要主动为界面文案生成 i18n key，优先直接使用原始文本。
2. 如果当前模块或项目已经明确采用 i18n 体系，并且新代码需要保持一致，则必须遵循现有国际化约定。
3. 不要在同一功能内混用两套文案策略：
   - 已使用 i18n 的模块继续保持 i18n
   - 未使用 i18n 的模块不要擅自局部引入 i18n
4. 如果是否需要 i18n 存在明显不确定性，应先查看同目录已有实现，再决定是否跟随。

---

## 4. 复用优先

1. 优先复用项目中已有的工具函数、通用组件、hooks、services 和成熟依赖，避免重复造轮子。
2. 对于常见且易出错的能力，如日期处理、集合处理、深层取值、格式化等，优先使用项目中已有成熟方案。
3. 若项目内没有统一方案，可优先考虑成熟第三方库，例如：
   - `lodash`
   - `dayjs`
4. 如果原生 API 已足够简单、清晰且不会显著增加维护成本，则优先使用原生实现。
5. 不要为了一个非常小的工具需求引入新的重量级依赖。

---

## 5. 模仿已有优秀实现

1. 改代码前，应先阅读与当前任务最相近的现有实现，包括：
   - 相邻文件
   - 同目录文件
   - 同类组件
   - 同类页面
   - 同类 hooks
   - 同类 service
   - 同类工具函数
2. 当功能与已有实现高度相似时，应优先参考并沿用已有设计，而不是自行发明新模式。
3. 若现有项目中存在多个实现方式，应优先选择：
   - 当前目录内已经使用的方式
   - 当前子系统内主流方式
   - 最近新增且仍在维护的方式
4. 模仿的是“被项目验证过的优秀实践”，不是机械复制；复用时仍要结合当前场景做必要收敛和简化。
5. 若发现现有实现存在明显设计缺陷，可以提出优化方案，但默认应先保证兼容性和一致性，而不是立即推倒重来。

---

## 6. 命名与可读性

1. 命名应尽量贴近业务语义，而不是只追求抽象和简短。
2. 变量、函数、类型、组件命名应优先与当前目录已有命名方式保持一致。
3. 不要在局部上下文中引入过于泛化的命名，例如：
   - `data`
   - `info`
   - `handler`
   - `utils`
4. 当某个命名需要结合业务上下文才能看懂时，应优先补足语义，而不是依赖注释解释。
5. 注释应用于解释“为什么这样做”，而不是重复代码表面含义。

---

## 7. 改动方式

1. 默认优先最小改动原则：只改与当前任务相关的内容，不顺手扩大重构范围。
2. 除非用户明确要求，否则不要擅自引入：
   - 大规模重构
   - 目录迁移
   - 框架替换
   - 风格统一类扫尾改动
3. 如果只需局部修复，就不要顺手扩散成全项目级调整。
4. 对已有稳定功能的改动，应优先控制影响面，并尽量保持调用方式不变。
5. 当改动存在兼容性风险时，应显式说明风险点和影响范围。

---

## 8. 何时读取本文件

以下场景应主动读取本文件：

1. 不确定当前模块是否该使用 i18n 时
2. 不确定该复用已有工具还是自己实现时
3. 不确定应采用哪种写法更贴近项目风格时
4. 准备在现有模块中新增代码时
5. 准备做非纯修复性的代码调整时

---

## 9. 不应写入本文件的内容

以下内容不应写入本文件，而应写入更局部的 `AGENTS.md` 或其他详细文档：

1. 某个具体业务模块的业务逻辑
2. 某个页面的链路经验
3. 某个目录特有的 review 结论
4. 某个组件特有的历史坑点
5. 某个接口、弹窗、路由、页面名相关的局部规则
