# component-design.md

## 1. 目标

本文件用于约束组件设计、逻辑组织、状态管理与封装边界。  
当任务涉及组件拆分、页面组织、hooks/utils/services 提取、复用边界判断时，应优先读取本文件。

---

## 2. 核心原则

1. 组件设计应优先保持职责单一、逻辑清晰、边界明确。
2. 不要将过多业务逻辑、数据处理、视图渲染、事件控制混杂在同一个组件中。
3. 组件拆分的目标是降低耦合、提升可读性和复用性，而不是机械拆文件。
4. 不要为了抽象而抽象；只有在明显带来收益时，才新增封装层。
5. 优先模仿当前项目中已存在的同类组件设计。

---

## 3. 组件职责划分

### 3.1 展示组件

展示组件应优先负责：

- 结构与样式渲染
- 基础交互反馈
- 接收外部数据并展示
- 将交互事件抛给上层

展示组件不应承担过多：

- 数据请求
- 复杂业务状态管理
- 大量数据转换
- 多分支流程控制

### 3.2 页面组件 / 容器组件

页面级组件或容器组件应优先负责：

- 组织页面结构
- 串联业务流程
- 协调多个子组件
- 管理页面级状态
- 调用 hooks / services / utils

### 3.3 hooks

适合抽到 hooks 的逻辑包括：

- 状态管理
- 副作用处理
- 页面交互流程
- 表单联动逻辑
- 可复用的数据装配逻辑

不适合抽 hook 的情况：

- 只在当前组件中出现一次的极简单逻辑
- 抽出后反而增加跳转成本
- 只是为了“显得更规范”而拆分

### 3.4 utils

适合放到 utils 的逻辑包括：

- 纯函数
- 与 UI 无关的数据转换
- 格式化处理
- 可复用计算逻辑

不适合放到 utils 的逻辑包括：

- 依赖组件状态的逻辑
- 强业务上下文流程控制
- 强依赖 React 生命周期的逻辑

### 3.5 services

适合放到 services 的逻辑包括：

- 接口请求封装
- 与后端协议直接相关的调用层
- 请求参数适配
- 响应结果标准化

不应把 services 写成：

- 夹杂 UI 逻辑的混合层
- 到处读写组件内部状态的黑盒层

---

## 4. 状态管理原则

1. 状态应尽量放在真正需要管理它的最小合理层级。
2. 不要为了“统一管理”而把本来只在局部使用的状态上提到页面顶层。
3. 也不要把明显跨多个子组件共享的状态强行塞回某个子组件内部。
4. 应尽量区分：
   - 服务端数据状态
   - UI 展示状态
   - 临时交互状态
   - 表单状态
5. 避免：
   - 重复状态
   - 可推导状态再次存储
   - 状态命名过于模糊
   - 多处同时维护同一事实源

---

## 5. 表单、表格、弹窗等常见模式

1. 若项目中已有成熟的表单、表格、筛选器、弹窗、抽屉、分页等通用模式，应优先沿用。
2. 不要在已有稳定模式之外再发明新交互组织方式，除非当前场景明确不适用。
3. 对于常见页面组合，如：
   - 列表页 + 筛选器 + 表格
   - 详情页 + 卡片区块
   - 按钮触发弹窗/抽屉编辑
   应优先参考项目中已有案例，而不是从零重组。

---

## 6. 拆分判断标准

出现以下任一情况时，可考虑拆分组件或逻辑：

1. 单文件承担了明显过多职责
2. 同一组件中同时存在大量：
   - 数据请求
   - 状态联动
   - 展示结构
   - 提交流程
3. 某段逻辑已经难以阅读或难以测试
4. 某段逻辑在多个地方重复出现
5. 同类流程未来明显会继续扩展

但如果拆分后会带来以下问题，则应谨慎：

1. 调用链过长
2. 文件跳转成本显著增加
3. 原本简单的逻辑被人为复杂化
4. 抽象出的层没有明确复用价值

---

## 7. review 时重点关注

当 review 组件设计时，应重点检查：

1. 职责是否单一
2. 逻辑分层是否清晰
3. 状态管理是否合理
4. 是否遵循项目现有模式
5. 是否存在多余抽象
6. 是否存在明显重复逻辑
7. 命名是否贴近业务语义
8. 后续维护是否容易定位修改点

---

## 8. 何时读取本文件

以下场景应主动读取本文件：

1. 组件代码明显过长时
2. 不确定是否该拆 hooks / utils / services 时
3. 不确定状态应该放哪一层时
4. 准备重构页面结构时
5. review 中涉及“组件封装是否合理”时

---

## 9. 不应写入本文件的内容

以下内容不应写入本文件，而应写入局部 `AGENTS.md`：

1. 某个具体页面的链路规则
2. 某个业务弹窗的特殊触发条件
3. 某个目录下独有的页面结构约定
4. 某个子系统内专属的状态流转逻辑
