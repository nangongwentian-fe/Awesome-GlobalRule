# code-organization.md

## 1. 目标

本文件用于约束代码组织方式，包括：

- 文件拆分
- 常量与类型放置
- hooks / utils / services 的组织
- 目录粒度控制
- 何时保留在当前文件，何时提取出去

目标是提升可读性、可维护性和与现有项目的一致性，而不是为了“更规范”而机械拆分。

---

## 2. 核心原则

1. 代码组织应优先服务于可读性与维护效率。
2. 优先遵循当前目录、当前模块已有的组织方式。
3. 拆分的前提是带来明确收益，而不是为了形式上的分层。
4. 若当前文件仍然清晰、逻辑集中、跳转成本低，则不必强行拆分。
5. 不要为了“未来可能会复用”而过度设计。

---

## 3. 常量与类型

### 3.1 常量

满足以下任一条件时，优先提取到当前组件目录下的 `const.ts`：

- 常量较多
- 常量会被多个文件复用
- 常量明显干扰主组件阅读
- 常量本身具有独立业务含义

以下情况可保留在当前文件：

- 数量很少
- 只服务于当前文件
- 放在文件内更容易理解上下文
- 提取出去反而增加跳转成本

### 3.2 类型

满足以下任一条件时，优先提取到当前组件目录下的 `types.ts`：

- 类型较多
- 类型会被多个文件复用
- 类型定义明显影响当前主文件可读性
- 类型本身具有独立业务语义

以下情况可保留在当前文件：

- 类型数量很少
- 只被当前文件使用
- 与当前组件高度绑定
- 拆出去没有明显收益

### 3.3 扩展名

1. `const` 与 `types` 文件一般使用 `.ts`
2. 仅当文件确实包含 JSX 时，才使用 `.tsx`
3. 不要无意义地把纯类型/纯常量文件写成 `.tsx`

---

## 4. hooks / utils / services 的组织

### 4.1 hooks

应考虑提取为 hook 的情况：

- 一段状态逻辑明显可复用
- 同一交互流程较复杂
- 副作用处理较多
- 逻辑已经影响组件主结构阅读

不应仅因为“组件有点长”就立刻拆 hook。  
如果拆出去后：

- 名称很泛
- 依赖很多外部上下文
- 阅读时仍必须来回跳转
- 没有复用价值

则说明不一定值得拆。

### 4.2 utils

适合放到 utils 的内容：

- 纯函数
- 数据转换
- 格式化逻辑
- 与 UI 状态无关的计算

不适合放到 utils 的内容：

- 强依赖业务上下文的流程控制
- 依赖 React 状态或副作用
- 需要读取组件内部状态的逻辑

### 4.3 services

适合放到 services 的内容：

- 接口调用
- 请求参数适配
- 响应结果标准化
- 与后端协议直接相关的处理

不应把 services 变成：

- 混杂 UI 行为的黑盒层
- 到处读取页面状态的耦合层
- 不清楚边界的“万能工具文件”

---

## 5. 文件拆分的判断标准

以下情况可考虑拆分：

1. 主文件已经明显承担过多职责
2. 某段逻辑已经可以独立命名
3. 某段逻辑未来有较大复用可能
4. 主文件阅读时频繁被大段无关细节打断
5. 类型、常量、工具函数已经形成自然边界

以下情况不建议拆分：

1. 只是几行简单逻辑
2. 拆分后文件数量明显增加但理解收益不大
3. 拆分后调用链更难追踪
4. 同一逻辑仍只在当前文件使用且上下文强依赖

---

## 6. 目录组织原则

1. 优先模仿当前模块已有目录结构。
2. 不要在同一项目中引入多套风格明显不同的目录组织方式。
3. 如果当前目录已经有稳定约定，例如：
   - `components/`
   - `hooks/`
   - `services/`
   - `utils/`
   - `const.ts`
   - `types.ts`
   则优先沿用。
4. 若某个目录只是为了存放一个文件而存在，应谨慎评估是否真的需要该层级。
5. 不要为了“更整齐”而堆叠无意义目录层级。

---

## 7. 单文件 vs 多文件

### 应偏向单文件的情况

- 逻辑较小
- 上下文高度集中
- 拆出去没有明显复用收益
- 当前文件仍然可读

### 应偏向多文件的情况

- 页面/组件职责明显增多
- 存在多段相对独立逻辑
- 需要分离请求、视图、状态、工具、类型
- 当前文件已经难以 review 和维护

---

## 8. review 时关注点

当 review 代码组织方式时，应重点关注：

1. 文件拆分是否真正降低了复杂度
2. 是否遵循当前目录已有风格
3. 是否出现过度抽象
4. 是否存在重复逻辑没有提取
5. 是否存在本该留在文件内却被机械拆出的情况
6. 常量、类型、工具函数位置是否合理

---

## 9. 何时读取本文件

以下场景应主动读取本文件：

1. 不确定常量或类型是否该拆出去时
2. 不确定 hook / utils / service 是否该提取时
3. 准备给某个目录整理文件结构时
4. 准备重构某个组件或页面的文件组织时
5. review 中涉及“文件组织是否合理”时

---

## 10. 不应写入本文件的内容

以下内容应写入更局部的 `AGENTS.md`，而不是本文件：

1. 某个目录专属的命名约定
2. 某个业务模块特有的拆分模式
3. 某个页面链路中的特殊文件布局
4. 某个组件专属的历史坑点
