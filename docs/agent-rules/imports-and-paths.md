# imports-and-paths.md

## 1. 目标

本文件用于约束：

- 导入路径的选择方式
- alias 与相对路径的使用原则
- 导入顺序与分组风格
- 路径改动的边界

目标是提升路径可读性、减少无意义跳转和保持项目一致性。

---

## 2. 核心原则

1. 导入路径应优先遵循项目现有约定。
2. 不要为了“更规范”而批量改动无关文件的导入路径。
3. 当前目录、当前子系统已有明显风格时，应优先保持一致。
4. 路径风格的目标是清晰、稳定、可维护，而不是绝对统一成某一种教条写法。

---

## 3. alias 与相对路径

### 3.1 已配置 alias 时

如果项目已配置路径别名，例如：

- `@/`
- `pages/`
- `components/`

则优先使用项目已有 alias，尤其在以下情况：

- 相对路径层级过深
- 多个 `../` 已明显影响可读性
- 同类文件中已经普遍使用 alias
- alias 更符合当前项目主流风格

### 3.2 未配置 alias 时

如果项目未配置路径别名，则：

1. 保持与现有代码一致
2. 不要为了当前一个小需求顺手引入新的 alias 体系
3. 不要在同一目录中混用“伪绝对路径”和相对路径风格

### 3.3 何时继续使用相对路径

以下情况继续使用相对路径通常更合适：

- 同目录文件
- 紧邻目录文件
- 当前目录已有明显相对路径习惯
- 使用 alias 反而增加理解成本

---

## 4. 避免的问题

应尽量避免：

1. 大量 `../../../../` 造成路径可读性差
2. 同一目录下同类文件使用两套完全不同导入风格
3. 为了改一处功能，顺手把大量导入路径全改掉
4. 人为制造“看上去统一，实际增加 diff 噪音”的路径整理

---

## 5. 导入顺序与分组

应优先参考当前项目已有顺序；如果没有明确约定，可采用以下常见顺序：

1. 第三方库
2. 项目级 alias 导入
3. 相对路径导入
4. 样式文件导入

如果当前项目已有成熟排序风格，应优先跟随，而不是强行改成另一套。

---

## 6. 路径改动边界

1. 如果当前任务不是“整理路径风格”，则不要顺手扩散成大规模路径清洗。
2. 若仅需修复功能，应只改必要导入，不要借机全目录重排。
3. 若必须调整路径，应保证：
   - 可读性确实提升
   - 与当前目录主流风格更一致
   - 没有引入额外兼容风险
4. 不要把“路径更短”误认为“路径一定更好”；判断标准仍是与现有项目的一致性和维护成本。

---

## 7. review 时关注点

当 review 路径与导入时，应重点关注：

1. 是否遵循当前项目约定
2. 是否存在多余深层相对路径
3. 是否出现不必要的大规模路径改动
4. 是否引入了项目内不常见的新导入风格
5. 导入顺序是否与同类文件保持一致

---

## 8. 何时读取本文件

以下场景应主动读取本文件：

1. 不确定应使用 alias 还是相对路径时
2. 发现一个文件中导入路径风格混乱时
3. 准备整理某个目录的导入风格时
4. review 中涉及路径可读性和导入一致性时

---

## 9. 不应写入本文件的内容

以下内容应写入更局部文件：

1. 某个目录专属 alias 使用习惯
2. 某个模块内特有的导入分组方式
3. 某个页面专属的路径说明
4. 某个组件链路的引用关系经验
