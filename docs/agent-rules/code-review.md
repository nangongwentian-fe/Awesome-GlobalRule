# code-review.md

## 1. 目标

本文件用于约束 Code Review 的关注点、表达方式和输出结构。  
Review 的目标不是展示知识点，而是帮助用户识别真正重要的问题，并给出可落地的改进建议。

---

## 2. 核心原则

1. Code review 不应只关注语法、格式或命名，还应重点关注逻辑设计、组件封装、复用边界、状态管理和复杂度控制。
2. review 的输出应尽量具体、可执行，而不是只给抽象评价。
3. 如果现有实现其实已足够合理，不要为了显得专业而强行提出低收益重构建议。
4. review 时应尽量结合项目中已有的更优实现，而不是只讲抽象最佳实践。
5. review 的重点是帮助用户做更好的决策，而不是单纯指出错误。

---

## 3. 重点关注维度

### 3.1 逻辑设计

检查：

- 逻辑是否清晰
- 分支是否过多
- 是否存在隐式耦合
- 是否容易出现边界条件遗漏
- 是否有重复流程未抽象

### 3.2 组件封装

检查：

- 组件职责是否单一
- 展示与业务逻辑是否混杂
- 是否出现过度封装或过度抽象
- 是否存在本该拆分却未拆分的部分
- 是否存在本不需要拆却被拆得过碎的情况

### 3.3 状态管理

检查：

- 状态是否放在合理层级
- 是否存在重复状态
- 是否把可推导状态再次存储
- 是否存在多个事实源
- 状态命名是否清晰

### 3.4 代码组织

检查：

- 文件拆分是否合理
- 常量、类型、工具函数位置是否合适
- 是否遵循当前目录已有模式
- 是否引入新的不一致组织方式

### 3.5 可维护性

检查：

- 后续是否容易定位改动点
- 新人是否容易理解
- 调用链是否过长
- 是否容易测试
- 是否埋下后续扩展成本

---

## 4. 输出方式

指出问题时，尽量按以下结构表达：

1. 当前问题是什么
2. 为什么这是问题
3. 会带来什么影响
4. 更好的替代方案是什么
5. 如果有多种方案，各自取舍是什么

---

## 5. 推荐表达方式

### 合适的表达

- “这里把展示逻辑、请求逻辑和状态联动放在一个组件里，导致后续维护时很难单独修改某一部分。”
- “这个状态实际上可以从已有数据推导出来，再单独存一份会增加不一致风险。”
- “当前拆分方式虽然更细，但并没有带来实际复用价值，反而增加了阅读跳转成本。”
- “这个实现和当前目录下其他页面的模式不一致，后续维护者会很难预期这类页面应该怎么写。”

### 不合适的表达

- “建议优化一下”
- “这里最好封装下”
- “这样写不太优雅”
- “建议用最佳实践”
- “这块可以重构”

这些表达太抽象，无法直接执行。

---

## 6. 多方案输出原则

如果存在多种可行方案，应给出：

1. 方案 A 是什么
2. 方案 B 是什么
3. 各自优点
4. 各自代价
5. 在当前项目背景下更推荐哪个

不要只给单一结论，尤其在以下场景：

- 是否拆 hook
- 是否抽公共组件
- 是否上提状态
- 是否引入新的工具层
- 是否调整目录结构

---

## 7. 不该做的 review

1. 不要只盯着命名和格式，忽略真正的设计问题。
2. 不要为了追求抽象最佳实践而无视当前项目约定。
3. 不要提出明显超出当前任务范围的大规模重构建议，除非用户明确要求。
4. 不要把个人偏好包装成必须修改的问题。
5. 不要在没有明确收益的情况下建议“全项目统一整理”。

---

## 8. 何时读取本文件

以下场景应主动读取本文件：

1. 用户明确要求 code review
2. 需要指出现有实现的问题
3. 需要给出替代方案和权衡
4. 需要判断某段实现是否真的值得重构
5. 需要输出更结构化的评审意见

---

## 9. 不应写入本文件的内容

以下内容应写入更局部文件：

1. 某个模块反复出现的专属 review 结论
2. 某个页面独有的坑点
3. 某条业务链路中特殊的实现建议
4. 某个目录专属的设计禁忌
